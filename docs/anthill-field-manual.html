    How it flows

    Eight situations, each drawn step by step: what happens first, what decides the next step, and where it branches. Under each, what it reads and writes, and where that is kept. The last chart shows every store at once.

    a step a decision where it should end up refused, or sent back

    A new agent picks up a task

    Somebody opens a new chat and asks: “make the Home map markers bigger.”

    Kept in Reads the work pages (.anthill/knowledge/work/), the map (.anthill/build/maps/codebase.json), the written rules and glossary (.anthill/knowledge/) and the live code. Writes nothing: every step here only reads.

    A change, from edit to tidy-up

    The agent makes the markers bigger and commits.

    Kept in The guard reads the settings (.anthill/anthill.config.json). The hook writes the map (.anthill/build/maps/codebase.json) and the open list (.anthill/build/upkeep.json). The keeper writes the glossary, notes and work pages (.anthill/knowledge/). The code itself lands in git, on this laptop.

    Pushing to GitHub

    The agent has three commits ready on a branch.

    Kept in The guard reads the settings (.anthill/anthill.config.json) and the commits being sent. Writes nothing in Anthill; the commits go to GitHub.

    A task that only reads

    An agent spends an hour measuring the news and learns that you call “gemini-sweep” the web sweep.

    Kept in The keeper writes the glossary (.anthill/knowledge/GLOSSARY.md) or a notes page (.anthill/knowledge/modules/), marked unconfirmed. You sign it by filling intent_attested_by at the top of the page.

    A piece of work through the board

    A planned piece of work: “draw the chain as four stops”.

    Kept in The board lives in .anthill/build/work/<project>/: the plan (contract.json), each unit's state (state/) and its brief (briefs/). The gate reads the map and the notes; a review is recorded in .anthill/audits/; an escalation is written to escalations/.

    When code changes under a written note

    Someone renames the function a rule is about: “the 650 km cut-off must never be lowered”.

    Kept in Reads the fingerprints recorded in the map and the citations on the notes pages (.anthill/knowledge/modules/). The keeper writes the corrected page.

    “Carry on”

    You open a new chat and type two words.

    Kept in Reads the work pages, your decisions and the traps (.anthill/knowledge/work/, decisions/, TRAPS.md), the board, and git's record of commits and uncommitted changes. Writes nothing.

    Installing Anthill in a new project

    A new project with some history, and nobody has written anything down.

    Kept in Writes the rules every agent reads (CLAUDE.md, AGENTS.md), the keeper (.claude/agents/anthill-keeper.md), which files agents may not edit (.claude/settings.json), the settings (.anthill/anthill.config.json), the charter (CONSTITUTION.md) and the three git hooks (.git/hooks/). The survey writes the map.

    Where everything is kept

    Every box on the charts above reads or writes one of these.

    Kept in All of it lives in the project folder: the rules files at the top, .claude/ for the keeper and the edit rules, and .anthill/ for everything else. .anthill/build/ is redrawn by Anthill and never edited by hand; .anthill/knowledge/ is written by the keeper and signed by you.

    VOL I

    The idea

    What Anthill is for, in the picture it is named after.

    Anthill

    A system that lets an AI agent work on a codebase it has never seen, without guessing, and without being trusted to say its own work is done.

    It lives outside LogiAstro, in ~/anthill, and is installed into the repository. It does three jobs: it keeps a map of the code, a memory of why the code is the way it is, and a set of rules and a board for doing work.

    The anthill picture

    The mental image the whole system is built around.

    • Chambers are areas of the code with one job each. See Chamber.
    • Pathways connect the chambers: what each one uses, and who uses it. See Pathway.
    • Tools are the skills an agent loads to know how to behave.
    • The foreman is the orchestrator: the board, the gate and the rules that decide what gets built where and when it counts as finished.

    The three jobs

    What the owner set as the expectation for Anthill on 26 September.

    • A knowledge graph, so an agent starting cold knows what it is walking into.
    • A guiding map, so it can see which code lives where and what connects to it.
    • An orchestrator, so it knows how to build in the anthill, take on new work, and live by the rules and skills.

    Starting cold

    An agent arriving with no memory of the project. Anthill is judged by how well it helps this agent.

    Every agent is cold at the start of a new chat. Tested on 26 September with fresh agents told nothing about Anthill: after the fixes, they found it by themselves through CLAUDE.md and anthill --help, used it, and got every task right. On 28 September a fresh agent told only "carry on" chose the right work through where.

    See orient, start, find-your-way.

    Authority chain

    Who outranks whom. Anything lower may never rewrite anything higher.

    Owner's instruction, in this conversation
  → CONSTITUTION.md        the charter, human-owned
    → .anthill/roles/      what each role may do
      → .anthill/contracts/  the units in flight
        → the code

    The owner's word is the highest authority. "The owner said so" means the owner said it, about this action, in this conversation. An approval given once does not carry forward to the next action.

    Two planes of authority

    On the work, the owner decides. On the map and the memory, the system decides.

    The system proposes, plans and builds what the owner approves; it never chooses what gets built. But it maintains its own map and notes without asking. Notes an agent writes record what the agent did, not what the owner wanted. Only the owner's signature turns them into agreed intent.

    Constitution

    The project's charter: name, what is being built, the stack, the architecture, key decisions.

    File: CONSTITUTION.md. Only the owner may edit it; agents are denied write access. anthill onboard is the one sanctioned way to fill a blank section, and it never overwrites an answer already given.

    Solo mode

    One agent working in place, alongside the owner. The mode LogiAstro runs in.

    Chosen by the owner on 22 September, after the field report found the tool had been built for a pool of background agents that nobody was running. In solo mode nothing escalates by counting failures, and work done commits in place instead of merging a separate copy. The other mode, pool, is still there for many agents at once.

    VOL II

    The map

    Where every piece of code lives, what it does, and what it connects to.

    Map auto

    A record of every source file in the codebase: its job, its pathways, its tests, and the history of changes to it.

    Built by reading the code, never by asking a model, so it is the same every time it is built. Redrawn automatically after every commit. It covers the Python backend and, since 26 September, the frontend screens.

    $ anthill map build
  wrote .anthill/build/maps/codebase.json -- 138 nodes

    Lives at .anthill/build/maps/codebase.json. You never need to open it; ask it with start.

    Chamber

    One area of the code with one job. LogiAstro has 24.

    A Python package like logiastro.sensing ("turning the world into signals with a location and a time"), or a group of screens like web.pages. A chamber's job comes from its own opening description. The map calls a single file a node.

    Node

    One file on the map, with everything known about it.

    • responsibility: its one-line job, from its own description
    • routes: what it uses; consumers: who uses it
    • tests: the test files that import it
    • history: the titles of the last 40 commits that touched it
    • symbols: every function and setting in it, with its description

    Pathway

    A connection between two chambers: one uses the other.

    Read from the code's imports. Change a chamber and every chamber on the far end of its pathways may break. relevance uses sensing, mapping and accounts; mapping is used by five others.

    History

    The titles of past commits, kept on the file they changed.

    The only text in the map written in the words people use when they ask for work: "stop shouting", "keep a beat's verdicts". Adding it more than doubled how often Anthill found the right file first.

    Frontend on the map

    The screens and their parts, read without a code compiler.

    Until 26 September the map read only Python, so every screen was invisible: 36 of 119 past tasks had nowhere to be sent. Anthill now reads each frontend file's opening comment, what it exports, and what it imports.

    Fingerprint

    A way of telling whether a piece of code changed shape, while ignoring changes inside it.

    Editing a formula inside a function leaves the fingerprint alone. Renaming it, changing its inputs, or changing what it calls breaks the fingerprint. That is how Anthill knows a note about the function may no longer be true. Since 26 September it also reads settings, not only functions, which cleared seven false alarms.

    Drift

    How a cited piece of code changed since a note was written about it.

    KindWhat happened
    missingThe code is gone.
    movedSame name, different file.
    reshapedIts inputs or outputs changed. The contract moved.
    rewiredIt calls different things now.
    recontextualizedDifferent code calls it now.
    verifiedNothing structural changed.

    Blueprint check reads only

    Checks every recorded statement about the code against the code as it is now.

    $ anthill blueprint
  stale  [451/454 claims checked]
  STALE reshaped  logiastro/mapping/corridor.py::CorridorDeriver

    Part of every gate. Three of LogiAstro's 454 claims are out of date today.

    VOL III

    Finding your way

    The commands an agent uses to go from a task to the right line of code.

    orient reads only

    The whole codebase on one page. The first thing a cold agent runs.

    What the product is, all 24 chambers with their jobs, uses and tests, what changed recently, where the notes are, the owner's words, how to run the tests, and the rules.

    $ anthill orient
  # You are in LogiAstro
  **logiastro.sensing** — turning the world into signals…  (33 files)
    - uses: logiastro, logiastro.mapping, logiastro.accounts
    - tests: tests/sensing, tests/relevance …

    start reads only

    Give it a task in your own words; it names the file, the line, and what a change there reaches.

    $ anthill start "change how a risk's tier is decided"
  file       web/src/components/risk/rank.ts
  look at    TIER_NAME, TIER_GLOSS, tierOf
  imported   9 files, Home and Risk floor included
  tested by  tests/risk-web/rank.test.ts

    It returns a card for the best match and lists the next candidates. The top one is right a little over half the time, so check the others before committing.

    Card

    The answer start gives: one file, and everything an agent needs before touching it.

    • you_are_here: the file and its job
    • look_here_first: the lines that best match the task
    • if_you_change_this: who uses it and which tests prove it. See What a change reaches.
    • rules_here: the written rules about this file
    • recent_changes: what people changed here lately
    • how_to_use_this: start here, then follow the pathways

    Look at another candidate: anthill card <node> --goal "<task>"

    Look here first

    The exact lines in a file that match the task, settings included.

    Added because agents reached the right file and then spent their steps searching inside it for the deciding line: GATE_KM, _cached, INSTRUMENTS. On eight tasks with known answers it named the deciding line six times.

    What a change reaches

    For the lines on a card: every other file that uses them, every test that names them, and a warning when nothing tests the file.

    $ anthill start "add a test for signing in"
  no test covers this file -- a change here is unproven until one does

    For a setting holding names, such as the list of weather sources, it also lists every other file that spells those names out. That is how the bug with marine readings was found. Agents said this was the part of Anthill that saved them the most time.

    Also: anthill impact <node> --symbol <name>

    Glossary

    The owner's words, and the code's words for the same thing.

    - **Home**, **home screen** → Chains, portfolio
- **Reports**, **feed** → Feed, signals
- **login**, **sign in** → token, session, auth

    The owner says "how far from a supply chain can news be before it goes to the model"; the code says "how close to a corridor a signal must be to be judged". No search closes that gap on its own. start adds the code's words to any task that uses the owner's, as a hint that never outvotes the task's own words.

    File: .anthill/knowledge/GLOSSARY.md. 27 lines, drafted by an agent, not yet confirmed by the owner. Only the owner changes the words on the left of the arrow.

    eval-map reads only

    The exam that measures whether the map works.

    Every past commit is a question: its title is the task, the files it changed are the answer. Each question is asked with its own commit hidden, so Anthill cannot read the answer key.

    $ anthill eval-map
  134 past tasks
  first guess right    57%   was 22% on 26 Sep
  right in top three   71%   was 30%
  within one step      81%

    Every change to how Anthill finds things is kept or dropped on this number. Four ideas were dropped because the exam got worse.

    Anthill versus plain search

    What the side-by-side tests found, stated plainly.

    On LogiAstro, an agent with ordinary search finds the right file as well as one with Anthill, because the code describes itself so well. What only Anthill gives is the picture before reading anything, what a change reaches, which tests prove it, the written rules, and the owner's words.

    VOL IV

    What is being worked on

    The map says where and the card says how. This volume is the what: the work in progress, what waits on the owner, what they decided, and how Anthill keeps all of it from going stale.

    where reads only

    The first command every agent runs. Every piece of work in progress, its next step, and what waits on the owner.

    $ anthill where
  **Put each story where it happened** — in progress · work/geotag-test-set
    - Next: After two days side by side, run compare, then switch.
    - Waiting on the owner: nationwide stories …
  ## What the owner has decided   7 decisions
  ## Traps                        what to avoid
  ## The job board                and where it disagrees with the pages

    Several chats work on one project at once and cannot see each other. This page is how they stay in step. Tested on 28 September with a fresh agent told only "carry on": it named the right work, waited for the step that wasn't due yet, and stopped at the decision that was the owner's.

    Work page

    One piece of work in flight: what it is, where in the code, how to do the next step, what waits on the owner, the traps, and its history.

    Lives in .anthill/knowledge/work/. LogiAstro has five: placement, reach, the new tests, the two-views redesign, and the sensing rebuild. They replaced notes that sat privately with one chat, where no other chat could read them and nothing could check them.

    State

    What a work page's next step is waiting on.

    StateMeans
    in-progressThe next step can be done now, even if later steps need the owner.
    waiting-on-ownerThe next step cannot happen without the owner.
    pausedThe next step waits on other work.

    A page once marked "waiting on owner" whose next step needed nobody made a chat report finished work as blocked. So the state describes the next step only.

    Page drift

    A work page records the commit it was last true at. Any later commit touching its code means the page may be behind.

      ⚠ This page may be behind: 1 commit(s) on its branch since it was last true

    Built because a note written at 13:21 ("the new rule isn't wired in yet") was false by 18:09, and nothing noticed. Only commits that touch the code a page cites count, so an unrelated commit doesn't raise a false alarm. The commit hook hands a stale page to the keeper to bring up to date.

    Work no page describes

    A branch with this week's commits that no work page names.

    Exactly what fooled the job board: a day's real work that nobody had written down. where names it out loud, and the next commit asks the keeper to write its page. A branch already inside a tracked one counts as that work's history, not separate work.

    Being edited right now

    Files with changes nobody has committed yet, and the work they belong to.

    Another chat may be working on them this minute, so an agent leaves them alone unless the owner says otherwise. Added after a chat spotted an uncommitted edit to the placement code only because it happened to look.

    Owner's decisions

    What the owner decided, in their words, and why. Only the owner changes these.

    Seven on LogiAstro, among them: the market is global; the supply chain screen is the product; opening a page never collects news; placement aims for 95% with no hand-typed lists. The keeper may point out that code now contradicts one; it never edits one.

    The board beside the pages

    The job board holds only work that was planned onto it. where shows it next to the work pages and names every disagreement.

      ⚠ The board says relevance.impl is ready, but its work page says
    paused: needs the owner's nationwide answer first. Follow the page.

    Installing in a new project

    One command, and Anthill knows the project before it finishes.

    $ anthill install --name "Shop" --stack "Python + React"
What Anthill knows already:
  map      2 places in the code, with their pathways and tests
  finding  a past task goes to the right file first time 100%
  explain  the largest code no page explains yet: shop/pricing.py
  work     recent work with no page yet: work/free-shipping

    The install switches on the guards, the keeper and the rules, then surveys the code. The first chat answers the charter questions and hands the lists to the keeper, which writes the first work page. Tested end to end on a new project on 28 September, which found and fixed five problems only a fresh install shows. anthill survey re-runs it any time.

    VOL V

    The memory

    Why the code is the way it is. The part the code itself cannot say.

    Knowledge page

    A page of rules about one area: what must stay true, and the exact code each rule is about.

    LogiAstro has two: mapping (4 rules) and sensing (17 rules). Both written by an agent, neither confirmed by the owner. They live in .anthill/knowledge/modules/.

    Business rule

    One statement on a knowledge page, with a permanent name.

    - **BR-LOGIASTRO-gate-cannot-cost-a-signal:** The pre-model proximity
  gate is 650 km … (sg: logiastro/sensing/scope.py::GATE_KM)

    A rule's name is never reused or renamed. A rule that stops applying is retired, with the reason.

    Citation

    The (sg: file::name) part of a rule, pointing at the code it is about.

    What makes a rule checkable. When the cited code changes shape, the blueprint check names the rule that may have gone stale. A rule with no citation is allowed, and counted as a statement nothing can check.

    verified_against

    The commit a page was last checked at.

    Written at the top of a page as logiastro@<commit>. Anthill compares each cited piece of code as it was then with how it is now.

    Owner's signature

    The intent_attested_by line on a page. Only the owner fills it; no agent ever may.

    Until the owner signs, a page records what an agent did, not what the owner wanted, and the area reports as "not settled". Today no page and not the glossary is signed.

    Footprint

    The files a page speaks for, such as logiastro/sensing/**.

    Two pages may not claim the same file.

    Lesson

    Something learned the hard way, filed by area so it comes back up when someone works there again.

    anthill lesson record · anthill lesson for <area>

    VOL VI

    Doing the work

    How a piece of work is planned, claimed, proven and closed. The one rule: an agent cannot say its own work is finished; a test does.

    Sprint

    A planned batch of work, split into units.

    anthill sprint new · add-unit · compile · set-gate · status

    Unit

    One piece of work with a boundary: the files it may touch, and the test that proves it.

    LogiAstro's board has 24 units: 21 done, 2 blocked, 1 escalated.

    Spec and impl

    Work is split in two: one unit writes the tests, another writes the code that passes them.

    The builder of the code can never edit the tests it has to pass. The field report counts this among the things that worked without anyone thinking about it.

    Owns

    The files a unit is allowed to touch.

    A unit that writes outside them is refused (exit 64). This produced the only genuine save the field report found: a unit was stopped from editing a file another, finished unit owned.

    Contract

    The compiled, enforced version of a sprint: every unit, what it owns, and what proves it.

    Lives in .anthill/contracts/, which agents may not edit.

    Board

    Where every unit stands: ready, claimed, gated, done, blocked or escalated.

    $ anthill work status --repo .     every session runs this first
$ anthill work next  --repo .     claim the next ready unit

    An honest note from the field report: about 5% of LogiAstro's work has gone through the board. Most is done on branches outside it.

    Gate

    The check that decides whether a unit is finished. It passes or fails; nobody argues with it.

    In order: did the unit stay inside its files, do its tests pass, is the map still true, and has it been reviewed.

    $ anthill work done --repo . --unit mapping.impl
  refused — no passing gate. Run the gate first.

    Exit codes

    The number a gate returns, and what to do about it.

    CodeMeaningWhat you do
    0PassedClose it with work done.
    1A test failed, or a review refused itFix the work.
    3Nobody has reviewed this yetNot your fault; costs no attempt.
    64Wrote outside its filesUndo that file; it belongs to another unit.
    65Asked to close without a passing gateRun the gate.
    66Two units claim one fileA planning bug. Escalate.
    67Already done or escalatedNothing to do here.

    Escalate and reopen

    Hand a stuck unit to a person, and bring it back once the cause is fixed.

    $ anthill work escalate --repo . --unit X --reason "what stopped you"
$ anthill work reopen   --repo . --unit X --reason "…" --by "owner"

    In the tool's first three weeks all three escalations were caused by the tool, not the work. Each was fixed at the source.

    Roles

    Planner, builder and auditor.

    RoleDoesFilled by
    plannerPlans and reports; talks to the owner; writes no codeclaude-code
    builderDoes one unit inside its filesclaude-code
    auditorReviews finished work; changes nothing; can refuse but not passclaude-code

    All three are the same tool here. A model reviewing its own work shares its blind spots, so its approval means little; the tests remain the real proof.

    Audit verdicts

    What a reviewer can record about a finished unit.

    VerdictMeaning
    PASSThe work is right.
    FAILThe work is wrong. Always refuses.
    PARTIALSome of it is right.
    DEVIATIONIt differs from the plan, recorded rather than refused.
    ARCH NOTEA design concern. Goes to the owner.
    VOL VII

    Keeping it tidy

    Every piece of work leaves the anthill as well documented as it found it, without slowing down the agent doing the work.

    upkeep reads only

    What a change left undone.

    • glossary: a line names code that is gone, or a screen has no line
    • knowledge: a rule cites code whose shape changed
    • tests: changed code that no test imports
    anthill upkeep: 17 thing(s) to bring up to date
  - tests: web/src/lib/theme.ts changed and no test imports it
  …

    An item stays on the list until its check passes, whoever fixes it.

    anthill-keeper

    A helper agent that does the upkeep in the background, so the agent doing your work never stops for it.

    1. The agent builds and commits. You get your work straight away.
    2. The commit lists what it left behind.
    3. The agent starts the keeper in the background and carries on.
    4. The keeper fixes the glossary and notes, suggests the missing tests, and reports in a few lines.

    It writes only the knowledge folder, so it cannot collide with the code being changed. It also writes and updates work pages, citing every file a statement depends on. It never writes tests, never changes the owner's words, and never signs a page. Defined in .claude/agents/anthill-keeper.md, so every new chat has it.

    First real run, 28 September: it recorded that "web sweep" and "wide sweep" are the owner's words for the gemini-sweep and gemini-wide collectors, and sorted 17 test gaps into four groups. It changed no code.

    Before any task ends

    Two questions every agent asks, whether it committed or not.

    • Is anything on the upkeep list? Hand it to the keeper.
    • Did I learn something the next agent shouldn't have to rediscover? A word the owner uses, why some code is the way it is, a trap. Hand the keeper one sentence.

    A task that only reads never commits, so no hook reminds it. This rule is the reminder.

    After-commit hook

    What runs automatically after every commit.

    It redraws the map, then runs anthill upkeep and prints the list in the terminal that made the commit. It can never stop a commit.

    The open list

    Upkeep that nobody has done yet, carried from one session to the next.

    Stored in .anthill/build/upkeep.json. anthill work status repeats it to every new session, so a skipped reminder becomes the next agent's first task instead of disappearing.

    VOL VIII

    Rules and guards

    What nobody may do, and which of those rules are enforced by a hook.

    main is protected refused

    Nobody commits directly on main. Work happens on a branch.

    main is what everyone branches from and merges into, so a change sitting on it is one nobody agreed to and everybody inherits.

    Pushing is the owner's act refused

    An agent never pushes unless the owner asked for that push.

    $ git push
  refused — pushing is the owner's act.
$ ANTHILL_OWNER=1 git push     the owner, one command at a time

    Put ANTHILL_OWNER=1 before each push, never in a shell profile. Otherwise every agent inherits owner status too.

    Secrets, junk and force pushes refused

    What no shared repository survives.

    • A commit adding a key, a token, a .env or a .pem. A secret is public from the first push.
    • A commit adding .DS_Store, __pycache__, node_modules or similar.
    • A push that rewrites history someone else already has.

    Checked against LogiAstro's whole history on 26 September: no secret or junk file was ever committed.

    Ownership guard off

    Refuses a commit of code that no claimed unit owns.

    Off on LogiAstro, because it would refuse every quick fix made outside the board.

    --no-verify

    The flag that skips every hook. Never used.

    A hook on one laptop runs the same program for the owner and the agent, so it cannot tell them apart. What holds is that nobody chooses to skip it. The only lock that binds everyone is branch protection on GitHub.

    Protected paths

    Files agents may never edit.

    CONSTITUTION.md, CLAUDE.md, AGENTS.md, .claude/**, .anthill/roles/**, .anthill/anthill.config.json, .anthill/contracts/**. They change only through the owner or a sanctioned command such as install, onboard or config set.

    Briefing, not asking

    How an agent takes an owner's instruction.

    • Say what is about to happen, then do it. Not "are you sure?".
    • One objection, once. If the owner confirms, it is settled.
    • Never do a smaller version of what was asked.
    • Report plainly what happened, including what went badly.

    VOL X

    Skills

    Reusable instructions an agent loads to know how to behave. The tools of the anthill.

    Load classes

    ClassWhen it loads
    bootstrapEvery session
    phase-scopedOnly during its phase: idea, planning or execution
    conditionalOnly when triggered: an audit, an escalation
    referenceNever automatically; looked up when needed

    anthill skill list --always-on · anthill skill get <name>

    find-your-way every session

    Tells a cold agent to run orient and start, and how to read the card.

    git-ground-rules every session

    The eight git rules no shared repository survives without.

    Commit before you pull. Branch, never main. main always works. A conflict is resolved when the tests pass, not when the markers are gone. Never rewrite shared history. No secrets. No junk. Never skip a hook, and never push unasked.

    git-playbook reference
